# КР №3 — итоговая проверка youDO

Дата: 22.11.2026, Europe/Moscow. Проверка относится к youDO, а не к примеру Student Hub.
КР №1–2 и их исходная PostgreSQL сохранены. Указанные ниже результаты получены
фактическим запуском команд и проверкой браузера, а не только чтением исходников.

## Автоматические проверки

| Проверка | Результат |
|---|---|
| Java 21 / PostgreSQL 16, `backend/compose.verify.yml`, отдельный Compose-проект и БД в tmpfs | 61 тест, 0 failures/errors/skipped |
| `npm --prefix frontend test` | 51 тест, все прошли |
| `npm --prefix frontend run build` | TypeScript + Vite, сборка прошла |
| Полный `backend/Dockerfile` через Compose | React + JAR собраны, оба healthcheck healthy |
| `git diff --check` | Без ошибок |

Команды для повторения из корня:

```sh
mkdir -p /tmp/youdo-kr3-maven
docker compose -f backend/compose.verify.yml run --rm verify
docker compose -f backend/compose.verify.yml down
npm --prefix frontend ci
npm --prefix frontend test
npm --prefix frontend run build
```

Тесты БД используют собственные auth_tests/csv_tests/orders_tests/analytics_tests и
migration_* схемы. Рабочая public-схема приложения не очищалась. Старые Maven/JavaFX
модули не менялись; их исторические проверки описаны отдельно в docs/review.md.

Новые регрессии подтверждают:

- `31.02.2027`, `29.02.2027`, `31.04.2027`, `2027-02-31` отклоняются, `29.02.2028` принимается;
- preview до 10 000 строк, отказ на 10 001 и на файле больше 5 MiB;
- файл с одной ошибкой не записывает даже корректные строки и не создаёт аудит;
- исходная version снимка используется при UPSERT, конфликт откатывает новые/изменённые заказы и аудит;
- usedAt откатывается вместе с файлом, после внешнего rollback тот же preview можно применить;
- два конкурентных apply одной проверки дают один 200 и один 404, без дубликатов;
- NEW_ONLY/categoryCode и совместимые CREATE_ONLY/category;
- Bean Validation в HTTP create/update и те же группы в OrderService для CSV;
- UI блокирует apply при invalidRows > 0 и сохраняет preview после временного 500;
- Swagger JSON/JS требуют ADMIN, VIEWER/EDITOR получают 403, аноним — 401;
- multipart после 401 повторяется один раз с тем же файлом, параллельные запросы используют один refresh.

## Обновление рабочего стенда

Перед обновлением сохранены приватный pg_dump и контрольные суммы в локальном
`.local/release-readiness/` основной рабочей папки. Дамп содержит секретные данные
и исключён из Git. Старый Docker-образ сохранён тегом
`youdo-kr3-backup:pre-release-20261122` для отката приложения.

Обновлён только проект `youdo-kr3` через `up -d --build --wait`; рабочий PostgreSQL
и volume не удалялись. Оказалось, что рабочая схема была V3: Flyway применил V4
(версии аккаунтов/категорий) и V5 (CSV preview), Hibernate validate прошёл.

После запуска проверены **все прежние поля** девяти таблиц:

| Таблица | Число строк до / после |
|---|---|
| users | 6 / 6 |
| orders | 12 / 12 |
| order_tags, order_notes | 0 / 0 |
| user_accounts | 1 / 1 |
| account_roles | 1 / 1 |
| refresh_sessions | 0 / 0 |
| audit_events | 4 / 4 |
| categories | 5 / 5 |

Контрольные суммы прежних полей совпали. У user_accounts/categories добавилось
поле version=0, поэтому полные JSON-хеши с новым столбцом отличаются ожидаемо;
сами прежние значения, включая пароли/активность/роли, не менялись. Рабочие логины
не сбрасывались. Миграции V1–V5 присутствуют, оба контейнера healthy.
Браузер на 8080 загрузил новый React и форму входа, health вернул UP,
неавторизованный запрос /api/orders — 401.

## Границы результата

Основные сценарии и обязательные тесты КР №3 пройдены. Это не нагрузочный аудит:
10 000 строк проверены как граничный размер preview, одновременный apply — на двух
запросах; несколько backend-реплик отдельно не разворачивались. Блокировка и
снимки находятся в общей PostgreSQL, данные приложения не хранятся только в памяти.
Для защиты остаётся пройти [сценарий](kr3-demo.md) командой и знать код своих частей.
