# КР №3 — сценарий защиты youDO

Стенд: Docker Compose, один origin для React и REST, отдельный PostgreSQL backend.
Полная последовательность занимает около 15 минут. Пароли задаются на машине показа,
в документе и Git их нет. Учётные записи входа отличаются от участников биржи.

## Подготовка

Запустить команды [README](../README.md). Для первого входа использовать временный
пароль из локального `.env`, сменить его и войти заново. Для существующего аккаунта
использовать уже установленный пароль: bootstrap его не меняет.

При наличии базы КР №2 перенести её по [инструкции](../backend/migration.md).
Для **отдельной новой демонстрационной базы** можно добавить двух участников:

```sh
docker compose --env-file backend/.env -f backend/docker-compose.yml exec -T db \
  sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  < backend/scripts/demo_participants.sql
```

SQL только добавляет отсутствующие email, существующие записи не меняет. Примеры CSV
используют `anna@mail.ru` (CUSTOMER) и `dmitry@mail.ru` (FREELANCER), категории DEVELOPMENT/DESIGN.
Если участников нет или роль другая, preview покажет ошибку. Все даты примера до 2030-12-31:
после этой даты их нужно заменить будущими.

Через «Пользователи» создать отдельные EDITOR и VIEWER со своими временными паролями.
В разных профилях браузера выполнить обязательную смену паролей и повторный вход.
Для permanent delete только на отдельном демонстрационном стенде явно задать
PERMANENT_DELETE_ENABLED=true и пересоздать backend; по умолчанию удаление выключено.

## Показ

1. **Запуск и база.** Показать `docker compose ... ps`, оба healthcheck, `/actuator/health`.
   Объяснить отдельный volume, Flyway V1–V5, `ddl-auto=validate`, сохранение числовых связей
   КР №1 и публичные UUID. JavaFX продолжает работать с прежней БД.
2. **Вход и роли.** VIEWER видит заказы/экспорт/аналитику, EDITOR — формы/CSV/заметки,
   ADMIN — аккаунты, категории, аудит и API. Прямой запрещённый HTTP-запрос тоже даёт 403.
   Временный пароль разрешает только смену, me и выход; после смены старые сессии отозваны.
3. **Заказ.** Создать заказ, выбрать категорию и заказчика из API, бюджет строкой,
   дедлайн, urgent и теги. Назначить исполнителя и перевести OPEN → IN_PROGRESS.
   Показать 400 для неверного бюджета и перехода, неизменяемого заказчика.
4. **Priority.** Финальные COMPLETED/CANCELLED — LOW. Остальные HIGH при urgent/просрочке,
   MEDIUM при дедлайне сегодня…+3 дня, иначе LOW. Москва, общий Clock и SQL CASE;
   priority не хранится и совпадает в карточке, фильтре и аналитике.
5. **Фильтры.** Найти слово только в описании; совместить q, категорию, статус, тег,
   priority и бюджет. q использует OR по полям, условия соединяются AND. Показать
   сортировку title/budget/deadline и серверные страницы; размер больше 100 отклоняется.
6. **Конкуренция.** Открыть две формы одного заказа, сохранить первую. Вторая получает
   409 и сохраняет введённый текст. Передаются исходная version и JPA @Version.
7. **Архив.** Архивировать, найти через фильтр, восстановить с тем же статусом.
   При включённой настройке ADMIN может удалить архивный заказ навсегда; аудит остаётся.
8. **Заметки и bulk.** Добавить/изменить/закрепить заметку. Автор и время серверные.
   Выбрать несколько заказов, показать архив/restore/статус/добавление и удаление тега.
   Ошибка одного элемента bulk не отменяет успешные, у каждого отдельная транзакция.
9. **CSV с ошибками.** На `/csv` загрузить `export/kr3-orders-invalid.csv`: корректная строка
   и ошибки даты/бюджета. «Применить» заблокировано. Проверить, что заказов не прибавилось.
10. **Валидный CSV.** Загрузить `export/kr3-orders-valid.csv`, NEW_ONLY, проверить 2 строки,
    применить один раз. Повторный apply того же preview отклоняется. При повторной проверке
    NEW_ONLY коды считаются ошибкой; UPSERT_BY_CODE обновляет их через OrderService.
    Если между preview/apply изменить заказ в форме — 409 и откат **всего** файла.
    Preview хранится 15 минут в PostgreSQL и переживает перезапуск.
11. **Экспорт.** В списке задать фильтр и сортировку, нажать «Экспорт CSV». Файл содержит
    все совпавшие строки, включая другие страницы, BOM/`;`/кавычки. Выгрузку можно
    импортировать обратно; для legacy-заказов сначала учитываются их просроченные дедлайны.
12. **Аналитика.** Сверить total=active+archived, urgentActive, средний активный бюджет,
    группы category/status/priority. Активные здесь — неархивные, включая финальные.
13. **Администрирование.** Создать аккаунт, изменить роль/active, сбросить пароль.
    Отключённый пользователь не входит; токен прежней версии больше не работает.
    Выключить категорию: старую ссылку можно оставить, новое назначение запрещено.
14. **Аудит.** Отфильтровать ORDER_CREATED/ORDER_CSV_IMPORTED, показать пользователя,
    UUID, время, безопасное описание, корреляцию, сортировку и страницы. VIEWER получает 403.
15. **Swagger.** ADMIN нажимает «API». Раскрыть `/api/orders`, Try it out → Execute:
    настоящий запрос выполняется от текущей сессии. Схема и ресурсы также закрыты ADMIN.
16. **Сохранность.** На отдельном стенде выполнить down без `-v`, затем up и повторить
    счётчики. Объяснить резервную копию перед обновлением и отсутствие DROP в миграциях.

## Что объяснять по коду

Controller/DTO → Service/transaction → Repository/Specification → PostgreSQL.
Общие проверки OrderService вызываются формой и CSV; preview не изменяет заказы.
Apply блокирует снимок, сверяет исходные версии и отмечает usedAt в одной транзакции
с заказами/аудитом; при ошибке всё откатывается. Тест конкурентного apply подтверждает
один успешный commit. CSV с ошибками не применяется частично.

JWT в памяти клиента, refresh в HttpOnly cookie для WEB, ротация и отзыв на сервере.
Один refresh на параллельные 401; файл FormData повторяется один раз; 403 не запускает refresh.
Пароли BCrypt, в логах/DTO/аудите нет секретов. Все ответы — DTO и единый JSON ошибок.

Результаты фактического прогона: [протокол](kr3-verification.md).
