# Подготовка к защите КР №2

Первый участок запуска подробно разобран в [четырёх коротких файлах для телефона](defense/README.md).

Разбор основан на текущем коде youDO. В проекте JavaFX-приложение подключается к PostgreSQL напрямую через JDBC: **JavaFX → контроллеры → сервисы → репозитории → PostgreSQL**. В Docker запускается PostgreSQL и отдельный контейнер для проверок. HTTP backend/REST-сервис в текущем youDO не реализован. Если преподаватель имеет в виду backend из своего отдельного примера, это другая система; не называйте нашу базу данных backend-сервером.

## Что предъявить

- Исходный код JavaFX: `src/main/java/ru/mirea/freelance/fx` и `src/main/resources/ru/mirea/freelance/fx`.
- Maven-проект: корневой `pom.xml`, запускаемый через `mvn javafx:run`.
- Схему базы и тестовые данные: `sql/schema.sql`, `sql/seed.sql`.
- Docker-окружение: `compose.yaml`, настройки генерирует `docker/setup.py`.
- Демонстрацию запуска, CRUD, поиска/фильтров/сортировки, валидации, статистики и CSV-экспорта.

## Запуск Docker и проверка PostgreSQL

Команды выполняются из корня репозитория:

```sh
python3 docker/setup.py
docker compose up -d --wait db
docker compose ps
docker compose exec -T db pg_isready -U youdo -d youdo
```

`docker/setup.py` создаёт локальный `.env` со случайным паролем, если файла ещё нет, и записывает отдельный `docker/db.properties` для JDBC. Существующий `src/main/resources/db.properties` не изменяется. Секретные локальные файлы исключены из Git и контекста сборки Docker.

`compose.yaml` запускает официальный PostgreSQL 16. Порт внутри контейнера `5432` опубликован как `127.0.0.1:55432` на хосте. Приложение с компьютера подключается к `127.0.0.1:55432`. Контейнер тестов подключается по имени сервиса `db:5432` во внутренней сети Compose.

При первом запуске на пустом volume контейнер PostgreSQL выполняет `sql/schema.sql` и затем `sql/seed.sql`: создаются таблицы, шесть пользователей и двенадцать заказов. Healthcheck использует `pg_isready` с TCP localhost, чтобы сообщить `healthy` после инициализации. Состояние можно дополнительно посмотреть так:

```sh
docker compose logs --tail=50 db
docker compose exec -T db psql -U youdo -d youdo -c 'SELECT count(*) FROM users;'
```

`docker compose down` удаляет контейнер и сеть, но сохраняет именованный volume с данными. `docker compose down -v` удаляет также volume. Для защиты не применяйте `-v`, если данные нужны. Не запускайте `schema.sql` и `seed.sql` вручную поверх нужной базы: schema удаляет прежние таблицы, seed очищает записи.

**Про backend:** команда `docker compose ps` показывает сервисы, описанные в нашем `compose.yaml`: PostgreSQL; при включённом профиле проверок — контейнер тестов. Отдельного HTTP backend там нет. Поэтому healthcheck PostgreSQL подтверждает состояние базы, но не REST API. Backend из преподавательского примера нужно запускать и проверять согласно его собственному архиву и Compose-файлу.

Полная локальная инструкция: [docker-local.md](docker-local.md). Статус примера преподавателя: [docker-demo.md](docker-demo.md).

## Запуск JavaFX

Для запуска требуются JDK 21, Maven 3.9+ и графический сеанс. Сначала проверь версии:

```sh
java -version
mvn -version
```

Maven должен использовать JDK 21. Если компиляция прошла для Java 21, а запускается JVM 17, возникнет `UnsupportedClassVersionError`: class file `65.0` означает Java 21, а Java 17 поддерживает class file только до `61.0`.

В этом окружении подготовленные JDK 21 и Maven 3.9.9 доступны так:

```sh
export JAVA_HOME=/tmp/youdo-tools/jdk/usr/lib/jvm/java-21-openjdk-amd64
export PATH="$JAVA_HOME/bin:/tmp/youdo-tools/apache-maven-3.9.9/bin:$PATH"
mvn -version
mvn -Dyoudo.db.config=docker/db.properties javafx:run
```

`pom.xml` задаёт Java release 21, зависимости JavaFX Controls/FXML, PostgreSQL JDBC, Apache POI и JUnit, а JavaFX Maven Plugin запускает `ru.mirea.freelance.fx.FxApplication`. Параметр `youdo.db.config` передаёт путь к внешнему файлу в JVM приложения. `DatabaseManager` читает его вместо classpath-конфига. Если параметр пустой, сохраняется прежний способ чтения конфигурации.

Тестовый контейнер запускается отдельно:

```sh
docker compose --profile test build verify
docker compose --profile test run --rm verify
```

Он использует JDK 21, Maven, Xvfb и настоящий PostgreSQL из Compose. Прогон включает JavaFX- и JDBC-тесты. Последняя проверка: 150 тестов, 0 ошибок, 0 падений, 0 пропусков. Xvfb предоставляет виртуальный дисплей UI-тестам без реального монитора.

## JavaFX: Stage, Scene, Node, FXML

`Stage` — окно верхнего уровня. В `FxApplication.start(Stage stage)` главная сцена помещается в него и вызывается `stage.show()`. Диалоговые формы заказов и пользователей открываются в отдельных модальных `Stage`.

`Scene` — содержимое окна. У сцены есть корневой узел, дерево интерфейса и список CSS-стилей. Здесь это корень, загруженный из `main.fxml`, и `app.css`.

`Node` — элемент дерева интерфейса: кнопка, поле, подпись, таблица или layout-контейнер. `VBox`, `HBox`, `GridPane`, `TableView`, `Button` являются узлами сцены.

FXML — декларативное описание интерфейса в XML. Оно отделяет структуру окна от Java-кода. Например, `main.fxml` собирает вкладки, а `fx:include` включает подэкраны `orders.fxml`, `users.fxml`, `statistics.fxml`. У корневого FXML указывается `fx:controller`; `fx:id` связывает UI-элемент с полем контроллера; `onAction="#onSave"` связывает действие кнопки с методом.

`AppContext.load()` создаёт `FXMLLoader`, задаёт `ControllerFactory`, загружает FXML. Фабрика создаёт контроллер через его конструктор `(AppContext context)`, в том числе для включённых через `fx:include` экранов. После создания контроллера FXMLLoader внедряет поля с `@FXML` и вызывает `initialize()`. Поэтому `initialize()` может настроить уже созданные FXML-элементы и обработчики.

`FxApplication` наследует `javafx.application.Application`. JavaFX вызывает её `start` после `Application.launch`. Метод создаёт `AppContext`, загружает `main.fxml`, применяет CSS и показывает окно. При завершении `stop()` закрывает контекст и его фоновые задачи.

## Архитектура и ответственность слоёв

```text
FXML / JavaFX controls
          ↓
     Controller
          ↓
       Service
          ↓
 Repository interface
          ↓
 Jdbc repository
          ↓
      PostgreSQL
```

- **Контроллер** связывает экран и приложение: читает значения полей, запускает действие, показывает список/ошибку/диалог. SQL и бизнес-правил в нём быть не должно.
- **Сервис** содержит правила предметной области: валидирует заказ, проверяет роли, смену статуса и ограничения на удаление.
- **Репозиторий** читает и изменяет сохранённые данные. Интерфейсы `OrderRepository` и `UserRepository` позволяют сервисам не зависеть напрямую от JDBC.
- **JDBC-репозиторий** содержит SQL, `PreparedStatement`, чтение `ResultSet`, преобразование результата в модели и отображение SQL-ошибок.
- **Модель** (`Order`, `User`, enum статусов и ролей) представляет предметные данные.
- **DatabaseManager** читает JDBC-параметры и создаёт подключения.
- **AppContext** собирает зависимости: репозитории → сервисы → контроллеры.

Короткий ответ преподавателю: «Контроллер отвечает за экран, сервис — за бизнес-правила, репозиторий — за SQL и хранение. Такое разделение позволяет отдельно проверять правила и не дублировать SQL в обработчиках интерфейса».

## Фоновые операции и исключения

JavaFX UI живёт в JavaFX Application Thread. Долгий SQL-запрос в этом потоке остановил бы перерисовку и обработку нажатий, поэтому `FxTasks` выполняет работу на однопоточном executor с именем `youdo-worker`. После успеха или ошибки callback возвращается через `Platform.runLater` в UI-поток. Контроллер обновляет элементы JavaFX только в callback.

Однопоточный executor исполняет задачи последовательно. Контроллеры во время чтения/записи показывают индикатор и блокируют неподходящие действия. При закрытии `FxTasks.close()` останавливает executor, а проверка `closed` не позволяет отправить запоздалый callback уже закрытому экрану.

Типы исключений отражают разные причины:

- `ValidationException`: значение не соответствует формату/ограничению ввода.
- `BusinessException`: операция нарушает правило системы, хотя сама запись может существовать.
- `EntityNotFoundException`: сущность с таким ID не найдена.
- `DatabaseException`: ошибка чтения конфигурации или взаимодействия с БД.

JDBC-слой переводит известные SQLSTATE в короткие сообщения: например, `23505` означает нарушение уникальности email, `23503` — нарушение внешнего ключа. Контроллер показывает `getMessage()` пользователю, а не сырой stack trace. Ошибка соединения не должна показывать пароль или полный текст драйвера.

## TableView и ObservableList

В `OrdersController` список строк объявлен как:

```java
private final ObservableList<Order> orders =
        FXCollections.observableArrayList();
```

`table.setItems(orders)` связывает список и таблицу. `ObservableList` уведомляет JavaFX об изменениях: `orders.setAll(newOrders)` обновляет строки автоматически. Обычный `ArrayList` сам по себе не сообщает таблице об изменениях.

Каждая колонка настраивается `setCellValueFactory`: функция извлекает нужное значение из `Order`. Например, заголовок берёт `getTitle()`, бюджет — `getBudget()`, дедлайн — `getDeadline()`. Для даты и денег задан `cellFactory`, который формирует человекочитаемый текст. Тип значения при этом сохраняется: числовая сортировка бюджета не становится лексикографической сортировкой текста.

После обновления контроллер получает новый снимок заказов и пользователей, обновляет карту пользователей, вызывает `orders.setAll(...)`, применяет текущую сортировку `table.sort()`, пытается восстановить выделенную запись и обновляет счётчик. Клиентские имена отображаются через `usersById`: в заказе хранятся ID, UI показывает имя.

## CRUD заказов и пользователей

### Заказы

- **Create:** `OrderFormController` собирает поля, контроллер запускает `OrderService.create`; сервис валидирует и вызывает `OrderRepository.save`; JDBC-репозиторий выполняет `INSERT`.
- **Read:** `refresh()` контроллера запускает `OrderService.find(query)`, получает результат и пользователей и передаёт снимок в UI callback.
- **Update:** форма открывается с заполненными значениями. Сервис находит текущую запись, делает копию `Order`, меняет поля и передаёт копию репозиторию. Так загруженный объект не изменяется до успешной записи.
- **Delete:** UI показывает подтверждение. После подтверждения сервис проверяет существование записи и вызывает удаление через репозиторий. Для пользователя ограничения FK отдельно защищают связанные заказы.
- **Назначение исполнителя** и **смена статуса** — отдельные действия, а не обычное редактирование полей.

Статусы заданы `OrderStatus`:

```text
OPEN → IN_PROGRESS → ON_REVIEW → COMPLETED
  └────→ CANCELLED       ↑
             IN_PROGRESS ←┘  возврат на доработку
```

Разрешены переходы: `OPEN → IN_PROGRESS/CANCELLED`; `IN_PROGRESS → ON_REVIEW/CANCELLED`; `ON_REVIEW → IN_PROGRESS/COMPLETED`. `COMPLETED` и `CANCELLED` финальные. Перейти в `IN_PROGRESS` нельзя без исполнителя.

### Пользователи

Форма пользователя создаёт, редактирует и показывает ошибки ввода. Email проверяется регулярным выражением и на уникальность. При редактировании текущий email разрешён: поиск дубликата исключает пользователя с тем же ID. Изменить роль пользователя нельзя, если он уже выступает заказчиком или исполнителем в существующих заказах. Удалить пользователя с активными заказами сервис запрещает; `ON DELETE RESTRICT` базы защищает ссылки и в других случаях.

## Поиск, фильтры и сортировка

Параметры поиска собраны в `OrderQuery`: текст, статус, категория. `OrderService.find()` загружает список через репозиторий и фильтрует Stream API:

```text
(название содержит текст ИЛИ описание содержит текст)
И статус совпадает, если он задан
И категория совпадает, если она задана
```

Сравнение текста не зависит от регистра: строка запроса и поля переводятся в нижний регистр через `Locale.ROOT`. `null`-описание пропускается безопасно. Незаданные условия представлены `null`; в фильтре это означает «все значения».

Фильтры статуса и категории запускают поиск после выбора. Кнопка обновления повторяет поиск с текущим `OrderQuery`; сброс очищает текст и оба выбора, затем делает поиск без фильтров. На текущем учебном объёме фильтрация сделана в памяти после `findAll`. Для большой базы поиск лучше выполнять SQL-запросом с пагинацией и подходящими индексами.

В таблице пользователь сортирует по нажатию на заголовок колонки. Для бюджета используется `BigDecimal`, для дедлайна — `LocalDate`, поэтому сравниваются числа и даты, а не их строки. После загрузки вызывается `table.sort()`, чтобы применить текущий порядок к новым данным. `OrderSortField` и методы сервиса также задают сортировку по бюджету, дедлайну и времени создания.

## Валидация

Проверка сделана на нескольких уровнях.

**Форма** показывает ранние ошибки возле поля и не закрывается после отказа. Для заказа проверяется непустое название, выбор категории и заказчика, корректное число и дата. Бюджет разбирается как `BigDecimal`; пробелы удаляются, запятая заменяется точкой. Дата разбирается строгим форматом `dd.MM.uuuu`, так что невозможная дата вроде 31 февраля отклоняется, а не нормализуется.

**Сервис** повторно проверяет правила независимо от конкретного UI:

- название заказа обязательно и не длиннее 150 символов;
- бюджет положительный, максимум `9999999999.99`, не больше двух значимых десятичных знаков;
- дедлайн задан и не находится в прошлом;
- категория задана;
- заказчик существует и имеет роль `CUSTOMER`;
- назначаемый исполнитель существует, имеет роль `FREELANCER`, не совпадает с заказчиком;
- переход в работу требует назначенного исполнителя;
- email пользователя соответствует формату, уникален, имя не пустое.

**PostgreSQL** служит последней защитой: `NOT NULL`, `UNIQUE`, `CHECK`, первичные и внешние ключи. Например, бюджет имеет тип `NUMERIC(12,2)` и `CHECK (budget > 0)`, email уникален, роль ограничена допустимыми значениями. Поэтому некорректные данные не попадут в БД даже при обходе формы или гонке двух операций.

## Статистика

`StatisticsController` вызывает `StatisticsService.collect()`. Сервис получает пользователей и заказы из репозиториев, затем считает показатели в памяти. Возвращается упорядоченная `LinkedHashMap`: название показателя → значение. Есть 13 показателей: всего пользователей, заказчиков, фрилансеров, всего заказов, количество по каждому из пяти статусов, средний бюджет, сумма бюджетов активных заказов, число просроченных и популярная категория.

Среднее считается через `BigDecimal`, сумма заказов сворачивается от `BigDecimal.ZERO`, среднее округляется до двух знаков `HALF_UP`. `double` не используется для финансовой арифметики, чтобы не накапливать двоичную погрешность.

Активный бюджет суммирует заказы, для которых `status.isFinal()` ложно. Просроченный заказ — дедлайн раньше `LocalDate.now()` и статус не финальный. Подсчёт по статусам перебирает все значения enum, чтобы показать ноль и для статуса, у которого сейчас нет заказов. Контроллер форматирует деньги/числа и отображает выбранные ключевые показатели карточками, остальные — таблицей.

## Экспорт CSV

Кнопка экспорта передаёт `ExportAction` копию текущего списка строк таблицы и копию списка пользователей. Значит, CSV соответствует видимому пользователю результату — текущим фильтрам и порядку строк. Экспортёр не перечитывает все заказы из базы.

`FileChooser` предлагает выбрать путь. Отмена просто прекращает операцию. Для имени без расширения приложение добавляет `.csv` и отдельно спрашивает подтверждение перезаписи. Запись выполняется в фоне через `FxTasks`.

`OrderCsvExporter`:

- пишет UTF-8 и BOM, чтобы Excel корректно распознавал кириллицу;
- использует `;` как разделитель и заголовки на русском;
- записывает бюджет с двумя знаками и десятичной запятой;
- вместо ID показывает имя и email заказчика/исполнителя;
- обрамляет кавычками значения с `;`, кавычками или переводом строки и удваивает внутренние кавычки;
- оставляет пустое поле, когда исполнитель не назначен;
- показывает понятную ошибку, если путь недоступен или запись не удалась.

## Сценарий демонстрации

1. Показать `docker compose ps`, прочитать состояние `healthy`, проверить `pg_isready`. Объяснить: PostgreSQL в Docker, JavaFX локально, соединение по JDBC.
2. Запустить JavaFX с JDK 21 и `-Dyoudo.db.config=docker/db.properties`. Показать вкладки заказов, пользователей, статистики.
3. Создать пользователя; изменить имя; ввести занятый email и показать валидацию.
4. Создать заказ с будущим дедлайном. Ввести плохую сумму или невозможную дату, показать сообщение и сохранение формы; затем исправить и сохранить.
5. Открыть редактирование, изменить поля, проверить отмену. Удалить запись, показав отмену подтверждения и затем само подтверждение на временной записи.
6. Назначить фрилансера. Показать недопустимую роль/отсутствие исполнителя и разрешённые переходы статусов.
7. Найти слово, встречающееся только в описании. Добавить фильтр статуса и категории вместе. Показать пустую выдачу и сброс.
8. Щёлкнуть заголовок бюджета и дедлайна для сортировки по возрастанию/убыванию.
9. Экспортировать отфильтрованный результат. Открыть CSV, показать BOM/кириллицу, бюджет и порядок.
10. Открыть статистику и объяснить среднее, активную сумму, просрочку и популярную категорию.

Используй отдельные временные записи и не запускай разрушающие SQL-скрипты на базе с нужными данными.

## Короткая речь для начала защиты

«youDO — JavaFX-приложение для биржи фриланса. Интерфейс описан в FXML, контроллеры обрабатывают действия пользователя, сервисы проверяют бизнес-правила, JDBC-репозитории выполняют SQL к PostgreSQL. База запускается отдельно через Docker Compose. UI-операции чтения и записи выполняются в фоновом потоке, а результат возвращается в JavaFX-поток. В приложении есть CRUD пользователей и заказов, совместный поиск с фильтрами, сортировка, статистика и экспорт видимых заказов в CSV».

## Типовые фрагменты кода

### ObservableList и TableView

```java
ObservableList<Order> items = FXCollections.observableArrayList();
table.setItems(items);
items.setAll(loadedOrders);
```

Список связывается с таблицей один раз; `setAll` заменяет содержимое и уведомляет JavaFX.

### Поиск по названию или описанию

```java
.filter(order -> text.isEmpty()
        || order.getTitle().toLowerCase(Locale.ROOT).contains(text)
        || order.getDescription() != null
        && order.getDescription().toLowerCase(Locale.ROOT).contains(text))
```

`&&` имеет приоритет над `||`: описание проверяется только если оно не `null`. Общий смысл: запрос пустой или совпало название или совпало существующее описание.

### Проверка денег

```java
if (budget.compareTo(BigDecimal.ZERO) <= 0) {
    throw new ValidationException("Бюджет должен быть больше нуля");
}
```

`compareTo` возвращает отрицательное число, ноль или положительное число. Для денег используется `BigDecimal`, а не `double`.

### Подсчёт просроченных заказов

```java
long overdue = orders.stream()
        .filter(order -> order.getDeadline().isBefore(LocalDate.now()))
        .filter(order -> !order.getStatus().isFinal())
        .count();
```

Stream проходит по элементам списка; каждый `filter` оставляет элементы, удовлетворяющие условию; `count()` считает оставшиеся.

### Безопасный JDBC-запрос

```java
String sql = "SELECT id, name, email FROM users WHERE id = ?";
try (Connection connection = db.getConnection();
     PreparedStatement statement = connection.prepareStatement(sql)) {
    statement.setLong(1, id);
    try (ResultSet result = statement.executeQuery()) {
        // Прочитать строки и превратить их в модели
    }
}
```

`?` — параметр запроса. `PreparedStatement` отделяет данные от SQL-текста, снижает риск SQL-инъекции и избавляет от ручного экранирования. `try-with-resources` автоматически закрывает соединение, запрос и результат.

### Проверка перехода статуса

```java
if (!current.canTransitionTo(next)) {
    throw new BusinessException("Такой переход статуса запрещён");
}
```

Правило сосредоточено в enum `OrderStatus`, поэтому UI и другие способы вызова сервиса не должны каждый по-своему разрешать переходы.

## Как отвечать, если просят изменить код

Перед набором кода проговори, где должна жить логика. Проверку обязательного поля можно показать в форме для ранней обратной связи, но бизнес-ограничение нужно продублировать в сервисе. SQL следует размещать в JDBC-репозитории. После этого назови входы метода, его результат и ошибочный случай.

Для нового фильтра удобно пройти цепочку целиком: добавить параметр в `OrderQuery`, передать его из контроллера, применить условие в `OrderService.find`, добавить/изменить тест сервиса и проверить отображение результата в таблице. Для новой колонки: добавить колонку в FXML, внедрить поле `TableColumn` в контроллер, настроить `cellValueFactory`, при необходимости задать форматирование `cellFactory`.

Не пытайся запомнить проект как набор строк. Запомни поток данных и причины разделения слоёв, затем по вопросу открой нужный класс и объясни конкретный метод.
