# Сервисы КР №2

`UserService` и `OrderService` сохраняют прежние методы CRUD, назначения исполнителя и переходов статусов. Бизнес-правила находятся в сервисах; графические формы передают ввод и показывают сообщения исключений. SQL остаётся в JDBC-репозиториях.

## Совместный поиск

```java
List<Order> visible = context.orders().find(
    new OrderQuery("сайт", OrderStatus.OPEN, OrderCategory.DEVELOPMENT));
```

`OrderQuery` — record с текстом, статусом и категорией. Поиск делает один `findAll()` и применяет Stream API:

- Текст без учёта регистра ищется в названии **или** описании. Пустое описание допустимо.
- Текст, статус и категория объединяются через **AND**.
- `null`/пустой текст и `null`-фильтры снимают соответствующие ограничения; `new OrderQuery(null, null, null)` возвращает все заказы, включая просроченные.
- `null` вместо самого объекта запроса — ValidationException с объяснением.
- Регистр преобразуется с `Locale.ROOT`, независимо от языка операционной системы.

Экран применяет сортировку TableView к найденным строкам и передаёт их копию в экспорт. Методы поиска КР №1 сохранены для консольного интерфейса.

## Валидация

Название заказа — до 150 символов после trim; имя — до 100, email — до 150. Email проверяется на вид `name@example.com`, отсутствие пробелов и повторной записи; при редактировании собственный email исключается из проверки уникальности. Семантика уникальности совпадает с существующей БД: регистр email не преобразуется.

Бюджет положительный, не больше `9999999999.99`, без значащей дробной части дальше копеек. `1.2300` допустим, `1.231` отклоняется. Сервис не округляет незаметно для пользователя: `stripTrailingZeros().scale()` определяет фактическую точность. Предел соответствует `NUMERIC(12,2)`.

При создании и редактировании заказа дедлайн не раньше текущего дня. Просматривать просроченные заказы можно. Категория, роль и связанные пользователи проверяются сервисами. Прежняя таблица переходов статусов и запрет начала работы без исполнителя сохранены.

## Роли и ошибки записи

Перед сменой роли сервис проверяет все связанные заказы, включая завершённые и отменённые. Заказчик существующих заказов не может стать исполнителем, а назначенный исполнитель — заказчиком. Без связей смена роли разрешена; при сохранении прежней роли можно редактировать имя и email.

Все проверки проходят до изменения данных. Для записи сервис создаёт отдельный объект с сохранением id, рейтинга/даты регистрации или служебных полей заказа. Если репозиторий отклоняет запись, ранее возвращённый объект остаётся прежним. После успешной операции используйте возвращённый результат либо перечитайте таблицу; не рассчитывайте, что старый объект изменился сам.

Удаление пользователя с активными заказами блокируется сервисом. Ссылки из завершённых заказов дополнительно защищены FK PostgreSQL; JDBC переводит это ограничение в понятную ошибку.

## Проверки и показ

```sh
mvn test
xvfb-run -a mvn -Dyoudo.fx.tests=true clean package
# На отдельной подготовленной БД:
xvfb-run -a mvn -Dyoudo.fx.tests=true -Dyoudo.db.tests=true \
  -Dyoudo.test.db.config=/absolute/path/check-db.properties clean package
```

Тесты проверяют OR/AND поиска, сброс фильтров, единственное чтение, пустое описание, разные регистры и локаль, границы строк и денег, смену роли для каждого статуса, неизменность данных после ошибок и прежний жизненный цикл заказа. Отдельный JDBC-сценарий проводит поиск и бизнес-операции через настоящие репозитории и удаляет только созданные им записи.

Форма пользователей проверена на повторный email, недопустимую смену роли, сохранение ввода после ошибки, отмену и блокировку закрытия при записи. Главное окно `main.fxml` включает заказы, пользователей и статистику. Экран заказов использует `find` для совместного поиска и фильтров; `startup.fxml` остаётся запасным экраном каркаса.

Проверено 20.10.2026 на JDK 21/Maven 3.9.9: полная сборка и 133 теста без ошибок и пропусков, включая 9 JavaFX-проверок и 2 сценария на отдельном PostgreSQL 16. Проверки БД не изменяли схему и демонстрационные записи.
