# 3. `AppContext`: сборка зависимостей

[Назад: FxApplication](02-fx-application.md) · [Оглавление](README.md) · [Дальше: FXML](04-fxml-practice.md)

Открой [AppContext.java](../../src/main/java/ru/mirea/freelance/fx/AppContext.java). Он создаёт один набор объектов для всего приложения и передаёт его контроллерам.

## Зачем это нужно

Если каждый контроллер сам создавал бы `DatabaseManager`, сервисы и фоновые потоки, код дублировался бы, а разные вкладки жили бы с разными экземплярами зависимостей. `AppContext` собирает их в одном месте. Поля `private final` показывают: после создания ссылки не переназначаются.

Цепочка конструкторов читается сверху вниз:

```text
new AppContext()
  → new DatabaseManager()
  → new JdbcUserRepository(database)
    new JdbcOrderRepository(database)
  → new UserService(...)
    new OrderService(...)
    new StatisticsService(...)
    new FxTasks()
    new ExportAction(this)
```

`this(...)` в конструкторе вызывает **другой конструктор этого же класса**. Так основной запуск передаёт настоящие JDBC-репозитории, а в проверках можно передать реализации интерфейсов `UserRepository` и `OrderRepository` без реальной базы.

Сервис зависит от интерфейса репозитория: ему нужны операции «найти», «сохранить», «удалить», а не конкретный способ выполнения SQL. Такой приём называют внедрением зависимостей: необходимые объекты передаются извне через конструктор. Это облегчает замену реализации и проверку бизнес-логики.

Методы `users()`, `orders()`, `statistics()`, `tasks()` и `exportAction()` возвращают созданные объекты контроллерам. Сам `AppContext` также имеет `close()`, который вызывает `tasks.close()`. Репозитории не держат постоянное открытое соединение; каждую операцию JDBC выполняет с отдельным соединением, которое закрывается после запроса.

## Как загрузчик получает контроллер с аргументом

Обычный FXMLLoader часто создаёт контроллер конструктором без параметров. Нашим контроллерам нужен `AppContext`, поэтому `AppContext.load()` задаёт `loader.setControllerFactory(...)`.

FXMLLoader сообщает фабрике класс нужного контроллера. Фабрика ищет публичный конструктор `(AppContext)`, вызывает его и передаёт текущий `this`. Это работает и для вложенных файлов через `fx:include`. Затем FXMLLoader внедряет поля с `@FXML` и вызывает `initialize()`.

Метод проверяет путь: он должен начинаться с `/`, то есть быть абсолютным путём **в classpath**. Если ресурс отсутствует, создаётся понятная ошибка с его именем. Если возникла ошибка чтения FXML, она заворачивается в исключение с указанием файла.

## Частые вопросы

**Когда открывается соединение с PostgreSQL?** При вызове `db.getConnection()` внутри метода JDBC-репозитория, а не при создании `AppContext`.

**Почему `OrderService` не создаёт `JdbcOrderRepository` сам?** Тогда сервис был бы привязан к JDBC и хуже проверялся бы независимо от БД.

**Почему фабрика нужна для `fx:include`?** Вложенные экраны тоже имеют контроллеры с конструктором `(AppContext)` и должны получить тот же набор зависимостей.

## Проверка понимания

1. Что именно создаёт конструктор `AppContext()`?
2. Чем `this(new DatabaseManager())` отличается от создания нового поля через `new`?
3. Почему сервис получает интерфейс репозитория?
4. Зачем `AppContext` реализует `AutoCloseable`?

<details>
<summary>Ответы для самопроверки</summary>

1. Цепочкой конструкторов создаются DatabaseManager, JDBC-репозитории, сервисы, FxTasks и ExportAction.
2. `this(...)` передаёт управление другому конструктору того же объекта, где собирается остальная цепочка.
3. Так сервис зависит от нужных операций, а не от конкретного SQL-хранилища; можно подставить другую реализацию.
4. Чтобы при завершении остановить фоновые задачи через `tasks.close()`.

</details>
