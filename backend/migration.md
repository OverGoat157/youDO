# Перенос прежних данных youDO

JavaFX продолжает работать с прежней БД. Backend использует отдельную БД и volume. Никогда не запускайте старые sql/schema.sql и sql/seed.sql поверх нужных данных: они удаляют/очищают таблицы. Flyway V1 берёт только CREATE TABLE из прежней схемы.

1. Запустите backend по README, чтобы Flyway создал новую схему. Таблицы users/orders в новой БД должны быть пустыми. Bootstrap-аккаунт не мешает переносу. Импорт выполняйте до начала работы через новый API.
2. Узнайте имена контейнеров: `docker compose ps` для КР №2 и `docker compose --env-file backend/.env -f backend/docker-compose.yml ps` для КР №3. Контейнеры PostgreSQL должны предоставлять POSTGRES_USER/POSTGRES_DB; скрипт запускает psql внутри контейнера без передачи пароля в аргументах процесса.
3. Создайте локальный снимок:

```sh
mkdir -p .local/kr3
python3 backend/scripts/transfer_legacy.py snapshot \
  --source-container youdo-kr2-db-1 --out .local/kr3/legacy.snapshot.json
```

Скрипт открывает REPEATABLE READ READ ONLY, читает users и orders в одном согласованном snapshot и создаёт файл с правами 0600. Существующий файл не перезаписывается. В снимке есть данные участников: он остаётся локальным и исключён из Git. Прежние TIMESTAMP WITHOUT TIME ZONE интерпретируются как UTC; это явное соглашение переноса, согласуйте другое преобразование до импорта, если исходная база использовала другую зону.

4. Загрузите в новую серверную базу:

```sh
python3 backend/scripts/transfer_legacy.py import \
  --target-container youdo-kr3-db-1 --snapshot .local/kr3/legacy.snapshot.json
```

Скрипт проверяет Flyway V3 и пустоту users/orders, блокирует таблицы от конкурентной записи, переносит явные старые ID/ссылки/суммы/даты, создаёт UUID и LEGACY-id, связывает категории по code, проверяет количество и значения, восстанавливает sequences и делает COMMIT. Неизвестная категория, нарушенные FK, недопустимая длина данных или ненулевая целевая база отклоняют весь импорт. Данные не обрезаются. Повторный импорт в непустую базу запрещён: он не является синхронизацией.

По завершении печатаются только числа строк, сумма бюджетов и количество уникальных публичных ID. При ошибке содержимое строк PostgreSQL намеренно не печатается, поскольку может содержать персональные данные. Для диагностики используйте локальную БД и её журналы.

Для источника вне Docker можно выгрузить JSON того же формата через psql (см. фиксированный SELECT в скрипте) или поднять восстановленную копию старой БД в отдельном PostgreSQL-контейнере. Скрипт не поддерживает произвольный pg_dump: нужен его snapshot формата 1.

## Проверка сохранности

Сравните число участников/заказов, SUM(budget), старые ID, customer_id/freelancer_id (включая NULL), даты и категории. Скрипт выполняет эти проверки до commit. Дополнительно проверьте уникальность public_id и code, отсутствие потерянных FK и корректность следующего ID после явного импорта. Остановите Compose без `-v`, поднимите снова и повторите счётчики. При отказе повторного переноса данные должны остаться прежними. Исходная БД после всех действий должна иметь те же строки.
