# Подготовка Дениса к защите КР №3

## Что показывать

1. `docker compose --env-file backend/.env -f backend/docker-compose.yml ps`: два healthy сервиса, отдельные volume/порты КР №3. Health не показывает секреты. Главная страница пока сообщает о подключении будущего frontend.
2. Три строки Flyway history: основа КР №1 → публичные UUID/категории → аккаунты/сессии/аудит. users/orders сохраняют старые BIGINT-связи, REST заказов должен использовать public_id.
3. Вход bootstrap-admin, mustChangePassword=true; бизнес-API закрыто 403. Смена пароля даёт 204, старый access перестаёт работать, нужен новый вход.
4. Login/me/refresh/logout. После refresh старый refresh даёт 401. После logout новый refresh даёт 401, ранее выданный access ещё живёт до 15 минут.
5. Запуск тестов в compose.verify: роли, Origin/cookie, ротация, два одновременных refresh, блокировка входов, отзыв доступа, аудит и перенос непустой основы.
6. Локальный протокол сравнения snapshot: 6/12 и сумма, ID/даты/связи, повторный импорт отклонён, после down/up данные сохранены. Точные факты — в verification.md.

## Как проходит запрос

CorrelationIdFilter создаёт/проверяет ID запроса. CORS проверяет origin и возвращает ошибки в общем JSON. AccessTokenFilter проверяет подпись/issuer/срок JWT, читает аккаунт, сверяет active/credentialsVersion, берёт актуальные роли, ограничивает временный пароль. Spring Security проверяет маршрут и роль. AuthController валидирует DTO и транспорт refresh. AuthService управляет транзакцией. AccountCredentialsStore работает через JDBC, RefreshSessionRepository/AuditEventRepository — через JPA; JDBC и JPA используют общий DataSource и транзакционный менеджер.

## Что объяснить своими словами

- JWT подписан, но не зашифрован. В нём нет пароля и авторизационного решения по устаревшим ролям: роли каждый раз читаются из БД. Компромисс — запрос к аккаунту на каждом защищённом HTTP, зато немедленное отключение доступа через версию.
- Access и refresh решают разные задачи. Access предъявляется явно в Authorization, refresh — случайные 32 байта, в БД только SHA-256. BCrypt нужен паролям с ограниченной энтропией; случайный refresh уже имеет достаточную энтропию.
- Транзакционная блокировка не позволяет двум refresh одновременно использовать один hash. Порядок блокировок аккаунт → сессия совпадает со сменой пароля/администрированием и снижает риск deadlock.
- HttpOnly запрещает чтение cookie скриптом, но сам по себе не защищает от CSRF. Поэтому WEB требует точный Origin; CORS не допускает чужую страницу; SameSite=Strict и JSON — дополнительные ограничения. ANDROID не допускается с Origin/cookie.
- BCrypt ограничен 72 байтами, поэтому Java length недостаточно для кириллицы. Политика проверяет UTF-8; новый пароль не равен старому. Bootstrap не сбрасывает пароль на каждом старте.
- История аудита и бизнес-изменение должны либо сохраниться вместе, либо вместе откатиться. Неудачный вход должен остаться даже при отказе операции, поэтому его аудит — REQUIRES_NEW. Не пишем в summary введённые пароли/токены/CSV.
- Flyway меняет схему по версиям и проверяет checksum, Hibernate validate сверяет JPA со схемой. Исходный DROP из КР №1 не является допустимым обновлением базы.
- 400 — неверные данные, 401 — нет действующего access, 403 — нет права/нужна смена пароля, 404 — нет ресурса, 409 — конфликт версии/целостности, 429 — блокировка попыток.
